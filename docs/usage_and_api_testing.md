# Advance-Text2SQL: User Guide and API Testing

This guide is for the local Docker environment seeded from `dataset_v2/sql/02_seed_data.sql`.
It explains how to start the system, sign in, submit Vietnamese questions, and verify
role-based behavior.

## 1. Start the system

From the repository root:

```powershell
docker compose up --build -d
docker compose ps
```

Wait until both `db` and `api` are healthy, then verify:

```powershell
Invoke-RestMethod http://localhost:8000/health
Invoke-RestMethod http://localhost:8000/health/ready
```

Both endpoints should return:

```json
{"status":"ok"}
```

Useful URLs:

| Service | URL |
| --- | --- |
| API documentation (Swagger) | <http://localhost:8000/docs> |
| API health check | <http://localhost:8000/health> |
| Frontend development server, when started separately | <http://localhost:5173> |

To stop the local services:

```powershell
docker compose down
```

## 3. Sign in and call the API

### Sign in

Use `POST /auth/login` with a username and password:

```powershell
$login = Invoke-RestMethod -Method Post `
  -Uri http://localhost:8000/auth/login `
  -ContentType 'application/json' `
  -Body '{"username":"user 161","password":"Passw0rd!"}'

$token = $login.access_token
```

The response contains an access token, refresh token, token type, and expiration.
Do not place either token in source code, issue trackers, or logs.

### Check the authenticated identity

```powershell
$headers = @{ Authorization = "Bearer $token" }
Invoke-RestMethod -Headers $headers -Uri http://localhost:8000/auth/me
```

This confirms the trusted user ID, application role, tenant, employee, department,
branch, and team used for permission checks.

### Submit a question

```powershell
$body = @{ question = 'có bao nhiêu nhân viên' } | ConvertTo-Json
Invoke-RestMethod -Method Post `
  -Uri http://localhost:8000/query `
  -Headers $headers `
  -ContentType 'application/json' `
  -Body $body
```

Successful responses return fields such as `query_id`, `columns`, `rows`,
`row_count`, `scalar`, and `truncated`. SQL text and bind values are intentionally
not exposed by the production API.

### Refresh or sign out

```powershell
# Refresh an expired access token.
$refreshBody = @{ refresh_token = $login.refresh_token } | ConvertTo-Json
$login = Invoke-RestMethod -Method Post `
  -Uri http://localhost:8000/auth/refresh `
  -ContentType 'application/json' `
  -Body $refreshBody

# Revoke the refresh-token session.
$logoutBody = @{ refresh_token = $login.refresh_token } | ConvertTo-Json
Invoke-WebRequest -Method Post `
  -Uri http://localhost:8000/auth/logout `
  -Headers @{ Authorization = "Bearer $($login.access_token)" } `
  -ContentType 'application/json' `
  -Body $logoutBody
```

## 4. Role-based test scenarios

Use the following questions in the frontend or `POST /query` after logging in with a
representative account.

| Question | Admin expected result | Current non-admin manager result | Purpose |
| --- | --- | --- | --- |
| `có bao nhiêu nhân viên` | `200` | `200`, department-scoped | Verify role and row scope |
| `tôi thuộc phòng ban nào` | `200`, one department | `200`, caller's department | Verify trusted caller identity |
| `chuyên viên 1 lương thấp nhất là bao nhiêu` | `200` | `403 PERMISSION_DENIED` | Verify sensitive-data policy |
| `top 5 sản phẩm bán chạy` | `200`, five products | `403 PERMISSION_DENIED` | Verify a disallowed cross-domain query is blocked |
| `top 5 danh mục được bán nhiều nhất` | `422` | `422` | Verify known unsupported fan-out-safe category aggregation |
| `tôi có thể xem những thông tin nào` | `422` | `422` | Verify non-data/capability questions are rejected cleanly |

The current role mapper translates `ADMIN_*` to the application role `admin` and
translates `HR_*`, `FINANCE_*`, `SALES_*`, and `SUPPORT_*` to
`department_manager`. Consequently, the latter roles share the same department
scope and standard-column allowlist today. In particular, an HR seed user is still
denied salary data. This is a known authorization-design limitation, not an NLP
failure; domain-specific application roles must be preserved before those policies
can differ.

## 5. API status and error contract

| HTTP status | Meaning | Typical `error_code` |
| ---: | --- | --- |
| `200` | Request succeeded | none |
| `401` | Missing, invalid, expired, or revoked authentication | `AUTHENTICATION_REQUIRED`, `INVALID_CREDENTIALS`, `INVALID_REFRESH_TOKEN` |
| `403` | Authenticated caller is not permitted to access the requested data | `PERMISSION_DENIED` |
| `422` | The request is ambiguous, unsupported, or invalid for the deterministic pipeline | `AMBIGUOUS_QUERY`, `UNSUPPORTED_QUERY`, `MISSING_ENTITY` |
| `503` | PostgreSQL or another backing service is temporarily unavailable | `SERVICE_UNAVAILABLE`, `SQL_EXECUTION_ERROR` |

For a non-`200` response, inspect `error_code`, `message`, and `query_id`. The
frontend may retain historical failed requests in browser local storage. Use a hard
refresh and submit the question again after changing the backend; old history entries
do not change retroactively.

## 6. Current validation baseline

The following checks were run against the local seeded Docker environment:

| Check | Result |
| --- | --- |
| Login for the 12 accounts in this guide | `12 / 12` returned `200` |
| Role/question API matrix | `72` requests: 12 active role users × 6 questions |
| Tenant isolation | Admin tenant 1 and tenant 2 returned their own employee and product records |
| Department isolation | Manager employee counts were limited to their own department |
| Sensitive and unsupported requests | Returned controlled `403` or `422`, never server errors |

```powershell

```
